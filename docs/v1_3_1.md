# ED Multi-Agent World Model

## v1.3.1 Simplified Boundary-Clean Architecture Design

*A modular, pluggable, extensible ED simulation architecture without unnecessary workflow complexity*

## 1. Executive Summary

This document defines the v1.3.1 architecture for an Emergency Department multi-agent world model system. The design intentionally avoids both extremes: it is not a throwaway MVP, but it also does not become a full hospital operations simulator. The goal is a runnable, maintainable, modular system with clear boundaries and thin interfaces.

The system has four LLM-based agents: clinician, nurse, patient, and relative. In v1.3.1, the clinician is the only agent that can propose medical treatment orders and diagnostic orders. Nurse, patient, and relative are verbal-only agents. Nurse remains the shadow executor role for clinician treatment orders, but nurse does not output physical actions. Patient and relative behavior actions are not modeled in v1.3.1.

- Physiology is updated only by the physiology transition engine.
- Emotion is updated only by a pluggable emotion transition engine, using conversation-only input.
- Diagnostic results come from the scenario test bank and are released after the ordered test's configured turnaround, with a default fallback.
- If no valid medical treatment order occurs in a turn, the physiology engine receives a conservative one-minute `no_action` input.
- All writes to `GlobalState` go through `StateManager` mutate methods; there is no `TurnDelta` object in v1.3.1.
- Action space is hierarchical and extensible: `family -> kind_hint -> params`. The existing 33 `kind_hint` values remain engine-facing labels, not a flat clinician-facing menu.

## 2. v1.3.1 Scope and Non-Goals

v1.3.1 is designed to run end-to-end while keeping future extension points clean. The following are intentionally excluded from v1.3.1:

- nurse workload, nurse skill, or complex nursing task queues
- explicit nurse physical actions
- patient or relative behavior actions such as refusal, removing oxygen, or blocking care
- test bundles or multi-test diagnostic orders
- treatment delays, onset, duration, or PK/PD curves
- relative emotion transition
- memory summarization or long-term memory retrieval
- structured disclosure-rule execution for patient symptoms/history
- teaching objective completion logic or complex termination rules

## 3. Core Design Principles

- **Single source of truth:** `GlobalState` is authoritative. LLM agents never directly mutate `GlobalState`.
- **Thin modules, clear boundaries:** Avoid `Manager`/`Policy`/`Checker` classes unless they solve a real v1.3.1 problem.
- **Pluggability by interface:** Agents, orchestrator, observation builder, physiology engine, emotion engine, action registry, validators, and logger can be replaced later.
- **No duplicate fact stores:** `known_facts` is the only source for clinical facts known to the care team. Memory does not store medical facts.
- **Structured runtime actions:** Clinician chooses `action family -> kind_hint -> params`. `raw_text` is `null` in v1.3.1 runtime actions.
- **Conversation and physiology are separate:** Verbal messages may affect patient emotion, but only treatment/no_action inputs affect vitals/features.
- **Implementation-first simplicity:** v1.3.1 uses fixed one-minute turns, diagnostic turnaround from the ordered test or default config, and same-turn treatment completion.

## 4. GlobalState v1.3.1

`GlobalState` is intentionally compact. It separates hidden scenario truth, current patient physiology, known clinical facts, patient emotion, and runtime process state.

```text
GlobalState
├── truth_state
│   ├── scenario_description
│   ├── patient_internal_state
│   └── test_bank
│
├── patient_state
│   ├── vitals
│   ├── features
│   └── status_flags
│
├── known_facts
│   ├── known_history
│   ├── known_allergies
│   ├── known_medications
│   ├── known_symptoms
│   └── available_results
│
├── psych_state
│   └── patient_emotion
│
├── agent_profiles
│    
│
└── runtime_state
    ├── turn_index
    ├── max_turns
    ├── messages
    ├── pending_questions
    ├── required_response_agents
    ├── pending_diagnostic_results
    ├── newly_available_results
    ├── last_turn_events
    └── termination_status
```

### 4.1 truth_state

`truth_state` contains hidden scenario truth. It is not directly visible to clinician or nurse unless disclosed through conversation or diagnostic release.

| Field | Purpose | Visible to whom? |
|---|---|---|
| `scenario_description` | Safe scenario-level case description and broad context. It may be used by LLM physiology engines as safe scenario context when it does not contain post-action targets. | Not directly shown wholesale to all agents; selectively used by `ObservationBuilder` and engines. |
| `patient_internal_state` | Structured patient-side truth: symptoms, chief complaint, hidden history/allergies/medications, and free-form disclosure guidance. | Patient agent sees relevant subset. Clinical team sees only disclosed facts. |
| `test_bank` | Scenario diagnostic repository. Each test has `name`, `result`, and optional `turnaround_turns`. | Clinician may see test names before ordering; results only after release. |

### 4.2 patient_internal_state

`patient_internal_state` gives the patient agent stable internal truth. Symptoms and hidden history should not be repeatedly inferred from `scenario_description` at runtime.

```yaml
patient_internal_state:
  chief_complaint: "shortness of breath"
  symptoms:
    - "shortness of breath"
    - "chest discomfort"
  hidden_history:
    - "hypertension"
    - "diabetes"
  hidden_allergies: []
  hidden_home_medications:
    - "metformin"
  disclosure_rules: >
    Free-form prompt guidance. The patient volunteers shortness of breath as the chief complaint.
    Chest discomfort should only be mentioned if directly asked about chest pain.
```

`disclosure_rules` is free-form prompt guidance consumed by the patient agent. It is not a deterministic rules engine in v1.3.1.

### 4.3 test_bank

v1.3.1 `test_bank` is deliberately minimal: no test code, no category, and no bundle. Each item contains `name`, `result`, and optional `turnaround_turns`.

```yaml
test_bank:
  - name: "ECG"
    result: "LVH and A.fib"
    turnaround_turns: 1
  - name: "Chest X-ray"
    result: "CHF"
    turnaround_turns: 2
  - name: "VBG"
    result: "pH 7.30, PCO2 35, PO2 95, HCO3 25, Lactate 2.0"
    turnaround_turns: 2
```

### 4.4 known_facts

`known_facts` is the only source of clinical facts known to the care team. Memory does not duplicate `known_facts`. Patient/relative disclosures and released diagnostic results update `known_facts` through `StateManager`.

- Patient or relative says a history/allergy/symptom fact -> `known_facts` may be updated.
- Diagnostic result released -> `known_facts.available_results` is updated.
- Hidden truth in `truth_state` does not automatically become `known_facts`.

### 4.5 runtime_state

`runtime_state` holds process state. v1.3.1 merges `conversation_state`, `turn_control_state`, and previous runtime process fields into this one structure to avoid deep paths and artificial subsystems.

**Runtime message/event boundary:**

`messages` are agent-spoken dialogue only. Examples: clinician explanation, patient answer, nurse bedside reassurance, relative question.

`last_turn_events` are system actions recorded for trajectory, observation, and debugging. Examples: diagnostic releases, nurse shadow executions, validation drops, physiology updates, and termination events.

If something was spoken by an agent, use `StateManager.add_message(...)`. If something happened in the simulator, use `StateManager.record_event(...)`.

**Pending question lifecycle:**

A `pending_question` is created when an agent verbal action directly asks another agent a question and sets `requires_response = true`.

A `pending_question` is resolved when the target agent produces any verbal response in a later turn, including a normal answer, uncertainty, refusal to answer, or inability to answer.

If multiple pending questions exist, the Orchestrator activates all required response agents. Within one target agent, pending questions are handled FIFO. Active agents may still stay silent if communication ability prevents response.


## 5. Modules and Interfaces

| Module | v1.3.1 Responsibility | Not responsible for |
|---|---|---|
| Orchestrator | Select active agents for this turn. Enforce required-response activation. Allow silence. | Does not decide medical content, update state, or choose treatment effects. |
| ObservationBuilder | Build role-specific observations for active agents only. | Does not mutate state or decide who is active. |
| StateManager | Only writer to `GlobalState` through small mutate methods. | Does not decide agent behavior or engine predictions. |
| ActionRegistry | Stores action families, `kind_hint` taxonomy, params schemas, and hierarchical menu data. | Does not validate role permissions or mutate state. |
| ActionValidator | Validates clinician action type, one-action-per-turn, test availability, `kind_hint`/params compatibility, and role permissions. | Does not build observations or run engines. |
| PhysiologyTransitionEngine | Predict patient vitals/features update from current patient state, safe context, and engine-facing action. | Does not generate clinician orders or dialogue. |
| EmotionTransitionEngine | Update patient emotion from conversation-only input. Default is `NoopEmotionEngine`. | Does not read vitals or change behavior actions. |
| TrajectoryLogger | Records agent outputs, validations, state mutations, engine calls, and errors for replay/debug. | Does not own state. |

### 5.1 StateManager mutate methods

v1.3.1 removes `TurnDelta`. The turn loop calls `StateManager` methods in order. `TrajectoryLogger` records these calls. This is simpler than atomic turn commits and is enough for a single-threaded simulation.

Example `StateManager` methods:

```text
add_message(message)
update_known_facts(fact_update)
create_pending_diagnostic_result(test_name, ready_turn)
release_diagnostic_result(test_name, result)
apply_physiology_update(engine_output)
update_patient_emotion(emotion_output)
record_event(event)
advance_turn()
```

`StateManager` remains the only writer to `GlobalState`. Agent outputs, validators, engines, and loggers do not mutate `GlobalState` directly.

### 5.2 Memory in v1.3.1

v1.3.1 memory is only a rolling conversation window. It may be implemented as a helper function or a thin `MemoryManager` wrapper.

```text
get_recent_messages(global_state.runtime_state.messages, N) -> list[Message]
```

No `case_memory`, no per-agent memory copy, no summary, no emotion-relevant memory, and no long-term memory in v1.3.1. `known_facts` is the only clinical fact source.

## 6. Role-Specific Observation Schemas

Orchestrator first selects active agents. `ObservationBuilder` then builds observations only for those active agents. Each role has a fixed observation shape; missing data is represented as empty lists or null values, not by changing schema branches.

| Role | Observation fields |
|---|---|
| clinician | current `patient_state`; `known_facts`; available diagnostic test names; `newly_available_results`; `recent_messages`; `pending_questions` requiring clinician awareness; `runtime_state.last_turn_events` |
| nurse | coarse current `patient_state`; `recent_messages`; `newly_available_results`; `last_turn_events`; `current_bedside_event_if_any` |
| patient | relevant `patient_internal_state` subset; current `patient_emotion`; recent messages addressed to patient or public; perceived bedside actions; communication ability flags |
| relative | relationship/profile if provided; family-side hidden info if scenario provides it; recent messages addressed to relative or public; coarse visible patient status |

The patient observation must not be a full `scenario_description` dump. It is a controlled view derived from `patient_internal_state`, recent conversation, emotion, and communication ability.

## 7. Orchestrator Policy

The Orchestrator is a lightweight turn-taking gate. It decides who is active, not what they say or what treatment does.

- Clinician is active every turn, but may choose no verbal action and no clinician action.
- Any agent directly asked a question requiring response becomes active on the next turn through `runtime_state.pending_questions` / `required_response_agents`.
- Nurse turn-start activation is limited to required responses and result-related reporting, such as `newly_available_results`. The same-turn nurse bedside verbal slot is not selected by the Orchestrator; it is a hard-coded reactive slot later in the turn after a valid clinician medical treatment order.
- Patient is active when required to respond. Patient speech is gated by `can_speak`/consciousness/age constraints.
- Relative is active only when required to respond or explicitly selected.
- All active agents may stay silent if they have no useful role-appropriate contribution.

```text
active_agents = orchestrator.select_active_agents(global_state)
observations = observation_builder.build_for(active_agents, global_state)
```

## 8. Action Proposal and Action Space

v1.3.1 action space is hierarchical and extensible. The 33 `kind_hint` values are engine-facing labels, not a flat clinician-facing menu.

```yaml
ClinicianProposal:
  verbal_action: optional
  action: optional
    - medical_treatment_order
    - diagnostic_order
    - null

NurseProposal:
  verbal_action: optional

PatientProposal:
  verbal_action: optional

RelativeProposal:
  verbal_action: optional
```

### 8.1 Clinician medical treatment order

```yaml
medical_treatment_order:
  type: "medical_treatment_order"
  family: "oxygen_support"
  kind_hint: "oxygen_support"
  params:
    oxygen_device: "NRB"
    FiO2: 1.0
    PEEP_used: false
    PEEP_cmH2O: null
```

Params may be null if unknown or unspecified. The selected `kind_hint` and params are authoritative for runtime.

### 8.2 Engine-facing action

Runtime `raw_text` is always `null` in v1.3.1. It remains only as a compatibility field for old engine schemas. Engines should rely on `kind_hint`, params, before state, `known_facts`, and safe scenario context, not `raw_text`.

```yaml
engine_facing_action:
  raw_text: null
  kind_hint: "oxygen_support"
  params:
    oxygen_device: "NRB"
    FiO2: 1.0
    PEEP_used: false
    PEEP_cmH2O: null
```

### 8.3 Diagnostic order

```yaml
diagnostic_order:
  type: "diagnostic_order"
  test_name: "ECG"
```

- One diagnostic test per turn maximum.
- No test bundles in v1.3.1.
- `test_name` must match a name in `truth_state.test_bank`.
- Before order/release, clinician sees test names only, not results.

## 9. Diagnostic Workflow

Diagnostic orders are information actions. They do not trigger physiology updates and do not trigger nurse reactive verbal slots.

- Clinician orders one test by name.
- `ActionValidator` checks that the test exists in `truth_state.test_bank`.
- `StateManager` creates a pending diagnostic result.
- Diagnostic turnaround is read from the ordered test's `truth_state.test_bank` item.
- If the ordered test item is missing `turnaround_turns`, runtime uses `DEFAULT_DIAGNOSTIC_TURNAROUND_TURNS = 2`.
- When ready, `StateManager` releases the result into `known_facts.available_results` and `runtime_state.newly_available_results`.
- Patient/relative do not automatically know results. Results can affect patient emotion only if spoken in conversation.

```python
DEFAULT_DIAGNOSTIC_TURNAROUND_TURNS = 2
```

```yaml
pending_diagnostic_result:
  test_name: "ECG"
  ordered_at_turn: 3
  ready_at_turn: 5

released_result:
  name: "ECG"
  result: "LVH and A.fib"
```

## 10. Nurse Shadow Execution

Nurse has no physical action output in v1.3.1. Valid clinician medical treatment orders are shadow-executed by the nurse role in the same turn. The trajectory records `ordered_by`, `executed_by`, and `execution_mode`.

```text
clinician medical_treatment_order
-> ActionValidator validates
-> StateManager records nurse shadow execution event
-> executed_by = "nurse"
-> execution_mode = "shadow_execution"
-> same-turn completion
-> physiology engine called at turn end
```

A medical treatment order may trigger an optional nurse bedside verbal slot. This verbal slot is usually addressed to the patient or relative, not the clinician. It may explain, reassure, or give simple bedside instructions. It may also be silent.

This nurse bedside slot is not part of turn-start Orchestrator activation. It is offered only after the clinician medical treatment order has been validated and shadow-executed. It cannot create physical actions or new orders.

## 11. Transition Engines

### 11.1 PhysiologyTransitionEngine

The physiology engine is a backend, not an agent. It updates `patient_state.vitals/features` based on current patient state, safe context, and engine-facing action.

Physiology input may include:

- `safe_scenario_context`: `scenario_description` and currently known clinical facts
- before `patient_state.vitals/features`
- `action.kind_hint`
- `action.params`
- `action.raw_text = null`

Physiology input must not include:

- pair labels or target vitals
- `source.modifier_text`
- unreleased diagnostic results
- `supporting_findings` not released through diagnostic workflow
- post-action targets

If there is no valid medical treatment order in the turn, the engine receives a `no_action` input.

```yaml
no_action engine-facing action:
  raw_text: null
  kind_hint: "no_action"
  params:
    elapsed_min: 1
```

v1.3.1 `no_action` is one-minute conservative progression. With no condition field, the engine should avoid large changes unless the current state is already critical. Stable fallback implementations may hold vitals for `no_action`.

### 11.2 EmotionTransitionEngine

The emotion engine is pluggable and conversation-only. It does not read vitals/features and does not produce behavior actions.

Emotion input:

- current `patient_emotion`
- patient profile/internal communication context
- verbal messages this turn
- recent messages window

Emotion output:

- updated `patient_emotion` only

Default implementation: `NoopEmotionEngine` returns unchanged `patient_emotion`. This allows the system to run before the external emotion engine is integrated.

## 12. Turn Loop v1.3.1

```text
Turn t:

1. Release ready diagnostic results
   - if ready_at_turn <= current turn
   - StateManager.release_diagnostic_result(...)
   - StateManager.record_event(type="diagnostic_release", ...)

2. Check termination
   - if is_terminated(global_state): stop

3. Orchestrator selects turn-start active agents
   - clinician always active
   - required response agents active from pending_questions
   - nurse active only for required responses or result-related reporting
   - nurse bedside verbal slot is not handled here

4. ObservationBuilder builds observations for turn-start active agents only

5. Active agents generate proposals
   - clinician: 0/1 verbal + 0/1 action
   - nurse/patient/relative: 0/1 verbal only

6. Validate proposals
   - invalid actions are dropped and logged with StateManager.record_event(...)

7. Commit primary verbal actions
   - StateManager.add_message(...)
   - StateManager.update_known_facts(...) if patient/relative disclosed facts
   - create or resolve pending_questions / required_response_agents as needed

8. Commit clinician diagnostic order, if valid
   - StateManager.create_pending_diagnostic_result(...)
   - no nurse bedside verbal slot

9. Commit clinician medical treatment order, if valid
   - StateManager.record_event(type="nurse_shadow_execution", ...)
   - treatment completes same turn

10. Optional reactive nurse bedside verbal slot
    - triggered only after a valid clinician medical treatment order
    - not selected by the Orchestrator
    - target patient/relative by default
    - StateManager.add_message(...) if nurse speaks

11. Emotion update
    - if any verbal messages this turn, call emotion engine
    - StateManager.update_patient_emotion(...)

12. Physiology update
    - if valid medical treatment order: call physiology engine with treatment action
    - else: call physiology engine with one-minute no_action
    - StateManager.apply_physiology_update(...)

13. Logging
    - TrajectoryLogger has recorded agent outputs, validation results, state mutations, and engine IO

14. Advance turn
    - StateManager.advance_turn()
```

## 13. Validation Semantics

Validation failures do not trigger retries in v1.3.1. The invalid proposal is dropped, the failure is logged, and the turn continues.

| Invalid item | v1.3.1 behavior |
|---|---|
| Invalid clinician medical treatment order | Drop action; no valid treatment exists, so `no_action` physiology progression applies. |
| Invalid diagnostic order | Drop diagnostic order; no pending result is created. If no treatment exists, `no_action` applies. |
| Invalid verbal action | Drop verbal action; continue turn. |
| Patient verbal blocked by `can_speak=false` | Drop or replace with null verbal; continue turn. |

## 14. Termination and Logging

### 14.1 Termination

v1.3.1 uses a simple function, not a termination module.

```python
def is_terminated(global_state):
    return (
        global_state.runtime_state.turn_index >= global_state.runtime_state.max_turns
        or global_state.patient_state.status_flags.is_alive == False
    )
```

### 14.2 Trajectory logging

`TrajectoryLogger` records the sequence of calls and events needed for replay/debugging. It does not own state.

Dialogue messages and simulator events are both logged, but they are not the same state type. Messages support conversation context; events support replay/debugging and may also appear in observations when relevant.

- turn_index and state snapshots as configured
- released diagnostic results
- orchestrator active_agents and activation reasons
- observations sent to each active agent
- agent raw outputs and parsed proposals
- validation results and dropped actions
- StateManager mutation calls
- emotion engine input/output
- physiology engine input/output
- errors and fallback usage

## 15. Future Extension Points

v1.3.1 keeps the extension path open without implementing the extensions now.

- Pharmacology-aware physiology engine with onset/duration/PKPD.
- Relative emotion transition.
- Patient/relative behavior actions such as refusal or cooperation.

Other future features should be discussed in a separate roadmap, not implemented or over-described in v1.3.1.

## 16. Suggested Implementation Milestones

| Milestone | Goal | Minimal tests |
|---|---|---|
| M1 GlobalState + StateManager | Implement compact `GlobalState` and mutate methods. | State writes only through `StateManager`; `runtime_state` paths are correct. |
| M2 ActionRegistry + ActionValidator | Support hierarchical clinician action and diagnostic order validation. | Valid/invalid treatment and diagnostic actions behave as specified. |
| M3 Diagnostic flow | Order one test by name, release after the test-bank `turnaround_turns` or `DEFAULT_DIAGNOSTIC_TURNAROUND_TURNS`. | Unreleased result hidden; released result enters `known_facts`. |
| M4 Orchestrator + Observations | Select active agents, build per-role observations. | Asked agent is active next turn; inactive agents receive no observation. |
| M5 Engine adapters | Run `NoopEmotionEngine` and default physiology engine/fallback. | `raw_text` is null; `no_action` uses `elapsed_min=1`. |
| M6 End-to-end turn loop | Run a scenario for several turns with logging. | No direct `GlobalState` mutation outside `StateManager`; logs include engine IO and validation failures. |

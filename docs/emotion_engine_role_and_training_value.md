# Emotion Engine 在急诊世界模型中的作用与教学价值

中文设计说明 · 基于当前仓库实现 · 2026-09-14

本文回答四个问题：emotion engine 在整个急诊模拟中承担什么职责；它接收什么、输出什么；这些输出如何影响后续模拟；它如何支持医学生训练和急诊沟通相关工作。文中分别标明当前实现、设计解释和未来应用，避免把设想当成已经验证的能力。

## 1. 核心定位：让沟通产生持续的模拟后果

当前 emotion engine 是一个由大语言模型驱动的、以收到的话语为触发条件的情绪状态转换模块。它根据听者原有情绪、说话者身份、当前话语及上下文，预测患者或家属接下来的四维情绪状态。

判断对象是听者在这次沟通后的情绪。一句措辞平静的风险告知，也可能使听者害怕；一句带着关心的询问，也未必消除听者已有的悲伤。因此，这项任务超出了对句子作正面／负面情感分类。

它在世界模型中的价值，是把沟通带来的心理反应保存为可检查的状态，再把状态提供给患者和家属的后续对话生成。这样，模拟不仅能表达“医护人员做了什么处置”，也能表达“医护人员如何解释处置，以及听者随后如何回应”。

需要区分三件事：

| 模块或任务 | 回答的问题 | 当前承担者 |
| --- | --- | --- |
| 情绪状态转换 | 听到这句话后，听者的情绪应如何变化？ | Emotion engine |
| 角色对话生成 | 带着当前情绪和可见信息，患者或家属下一次会怎么说？ | Patient / relative agent |
| 教学评价 | 学生的沟通是否准确、清楚、尊重患者并达到教学目标？ | 需要另设评价标准和教师评审；emotion engine 不能独立完成 |

因此，engine 输出的 `fear=present` 是一个模拟状态，不是医学生的分数，也不是对真实患者心理状态的测量结果。它预测收到话语后的反应，并没有读取真实听者随后发生的行为来确认这一预测。

## 2. 它在完整模拟流程中的位置

系统存在两条职责不同的状态更新路径：

```text
临床处置 → 生理适配器与引擎 → 患者生理状态更新
沟通话语 → 情绪适配器与引擎 → 患者／家属情绪状态更新

更新后的状态 → 各角色下一次可见的观察 → 后续对话与决策
```

这是逻辑职责图，不表示两条路径在代码中同时运行。实际调用由 turn loop 排序；患者情绪达到终止条件时，本轮可以提前结束，跳过后续生理更新。

在启用真实情绪适配器的运行中，主要流程如下：

1. 医生、护士、患者或家属的发言被提交为带有 `speaker`、`recipient`、`content` 的消息。
2. Turn loop 根据患者是否能感知对话、家属是否在场等条件，决定是否调用相应角色的情绪适配器。
3. Adapter 逐条处理明确发给该角色、且不是该角色自己说的消息。
4. Engine 预测新的四维情绪，adapter 将结果转换为世界模型的 `AgentEmotion`。
5. `StateManager` 写入 `GlobalState.psych_state`，并可记录 `emotion_update` 事件。
6. 后续构建患者或家属观察时，读取更新后的情绪；角色生成器据此生成下一次回应。

情绪更新不会重新生成已经提交的台词，也不直接决定谁获得发言机会。发言机会由 Orchestrator 等流程控制，更新后的情绪在角色后续被调用时发挥作用。

**启用条件必须明确。** `IntegrationRunner` 在没有注入情绪引擎时使用 `NoopEmotionEngine`，仅复制原状态。在 `generate_utterances.py` 中，`--emotion` 才会接入患者和家属的真实 emotion adapter。引擎本身的默认提示策略是 `zero_shot`，不等于每次运行整个模拟都会调用真实情绪引擎。

代码依据：[turn_loop.py](../ed_world_model/orchestration/turn_loop.py)、[emotion_engine_adapter.py](../ed_world_model/adapters/emotion_engine_adapter.py)、[runner.py](../ed_world_model/orchestration/runner.py)、[generate_utterances.py](../generate_utterances.py)。

## 3. 它表示什么情绪状态

患者和家属各自拥有一份状态，互不共用。医生和护士当前不携带这四维情绪状态。

| 维度 | 当前定义关注的内容 | 教学分析中可讨论的问题 |
| --- | --- | --- |
| `fear` | 健康、安全、生存、威胁和失控 | 听者是否理解危险？是否出现不必要的恐吓或无根据的保证？ |
| `sadness` | 已发生或迫近的损失、悲伤、无助 | 沟通是否允许合理的悲伤存在，并回应具体的损失？ |
| `overwhelm` | 超出处理能力的信息或情绪负担 | 信息是否过密？解释是否分段？是否确认理解？ |
| `shame` | 被指责、被评判、暴露、羞辱和尊严受损 | 是否在获取必要信息时避免对人格作判断？ |

每个维度独立取三个有序值：

| 等级 | 当前语义 |
| --- | --- |
| `absent` | 该情绪不存在 |
| `present` | 该情绪存在，从轻微到强烈但尚未达到危机程度 |
| `extreme` | 严重到影响继续参与的危机状态；当前引擎将该维度维持在 extreme，不允许回落 |

独立维度允许 fear 与 sadness 同时存在，不要求模型只选一种“主情绪”。但这四个维度不是完整的人类心理模型，也没有单独表示信任、理解程度、愤怒、疼痛或合作意愿。不能把 `overwhelm=absent` 直接解释为“已经理解”，也不能把 `fear=present` 直接解释为“拒绝治疗”。

在状态设计中，角色资料与 traits 描述相对稳定的个体特点，emotion 描述此刻的反应，最近消息提供对话上下文。临床团队已经获知的事实仍由 `known_facts` 管理；情绪更新由 `StateManager` 写入 `psych_state`，不会把模型的情绪解释直接变成新的诊断或病史事实。

`init_emotion()` 当前不调用 LLM，直接返回四项均为 absent 的起点。世界模型默认状态也是如此。这是为了建立统一的模拟起点，并不意味着现实中的急诊患者初诊时没有恐惧或悲伤。若调用方传入其他当前状态，默认 adapter 会使用传入的状态；未来教学场景可以设计不同起点，但应明确其来源。

代码依据：[emotion_engine.py](../emotion_engine.py)、[global_state.py](../ed_world_model/state/global_state.py)。

## 4. 输入是什么：区分适配器输入与模型实际看到的内容

### 4.1 世界模型交给 adapter 的输入

| 输入 | 来源与作用 |
| --- | --- |
| 当前情绪 `current_patient_emotion` | 当前角色的 `AgentEmotion`；这个参数名也用于家属，不表示家属共享患者状态 |
| `conversation_input` | 当前待处理的消息列表，包含说话者、接收者和话语 |
| `recent_messages` | 最近消息，用于构造对话上下文 |
| `patient_profile_context` | 对应角色的 profile；可包含 persona、description、traits |
| Adapter 配置 | `agent_role`、scenario、模型调用函数及 prompt strategy |

Adapter 在代码层过滤自身发言和接收者不匹配的消息。当前严格要求 `recipient == agent_role`；公开消息或其他接收者不会自动成为直接更新触发。历史对话的可见性仍有需要修正的边界，见第 10 节。

患者死亡、无意识或镇静时，turn loop 通常冻结其情绪；同轮镇静前已经听到的话语有专门的保留处理。三岁以下儿童当前不作为情绪对话角色，主要跟踪在场家属。这些是本模拟的实现约定，不是对现实儿童情绪能力的结论。

### 4.2 `step_emotion()` 的输入

可以把单次转换写为：

```text
下一情绪 = F(当前情绪, 当前话语, 听者身份, 说话者身份,
             临床文字上下文, 最近对话, 固定规则与提示策略)
```

| 输入 | 实际用途 |
| --- | --- |
| `trajectory.state` | 四种情绪的当前等级，是本次更新的起点 |
| `trajectory.agent_role` | 指定更新 patient 还是 relative |
| `utterance` | 本次需要评分的单条话语 |
| `speaker_role` | 说明话语由谁说出；自身发言会被拒绝 |
| `clinical_context` | 听者与场景的文字背景；adapter 会组合 scenario 和角色资料 |
| `dialogue` | 对话文字，用于理解指代、先前告知和当前话语的意义 |
| `prompt_strategy` | 选择 zero-shot、few-shot 或当前名为 react 的额外指导 |
| `llm_call` | 执行模型调用的可替换函数；可以在本地检查时换成模拟函数 |

`EmotionTrajectory` 可以携带历史状态和解释，但当前 prompt builder 不会把完整的 `trajectory.history` 自动发给模型。明确进入提示词的是当前四维状态及上述文字输入。

**“由对话驱动”需要准确理解。** 当前更新函数没有直接接收实时 vitals 向量；初始化函数保留的 `initial_vitals` 参数现在也不参与计算。但 scenario/clinical_context 的文字仍可能描述病情、症状或检查结果。因此，“不直接读取实时生命体征”不等于“完全没有临床信息”。这些背景应帮助解释话语和听者理解能力，而不应自动成为听者已经获知的新事实。

代码依据：[emotion_engine.py](../emotion_engine.py)、[emotion_engine_adapter.py](../ed_world_model/adapters/emotion_engine_adapter.py)、[turn_loop.py](../ed_world_model/orchestration/turn_loop.py)。

## 5. 输出是什么：模型结果、轨迹与世界状态

模型被要求返回完整的新状态，以及判断证据和解释。下面是用于说明接口的示意，不是实际运行结果或人工标准答案：

```json
{
  "new_state": {
    "fear": "present",
    "sadness": "absent",
    "overwhelm": "absent",
    "shame": "absent"
  },
  "evidence": "检查发现一个需要尽快处理的问题",
  "reasoning": "新告知的威胁使 fear 从 absent 变为 present；其他维度保持原等级。"
}
```

这里假设原状态四项均为 absent，话语告知了新的风险，但没有提供足够的损失、超负荷或羞辱线索。真实标签仍需要结合完整上下文并由评估标准校准。

`step_emotion()` 解析响应后返回新的 `EmotionTrajectory`，包括更新后的 `state`、追加后的 `history`、`last_evidence`、`last_reasoning`，并保留初始化说明。它会将已经处于 extreme 的维度强制保持为 extreme。

Adapter 输出的是世界模型的 `AgentEmotion`：四个等级加可选 `notes`。当前 adapter 把本批话语的 reasoning 拼接进 notes，但没有把每条 evidence 和完整逐句状态轨迹都独立写入 `GlobalState`。评估脚本会另行保存 evidence 和 reasoning；运行日志能记录轮级状态与事件。正式教学若需要逐句回放，应增加专门的教学记录，而不能假定当前日志已经完整保存所有中间转换。

`evidence` 和 `reasoning` 是模型生成的解释，可供检查和讨论；它们不是独立验证的心理事实，也不是模型内部推理过程的可靠记录。

代码依据：[state_manager.py](../ed_world_model/state/state_manager.py)、[emotion_engine_adapter.py](../ed_world_model/adapters/emotion_engine_adapter.py)、[evaluate_emotion_engine.py](../tools/evaluate_emotion_engine.py)、[generate_utterances.py](../generate_utterances.py)。

## 6. 输出如何影响整个世界模型

### 6.1 让患者和家属的反应具有跨轮次连续性

`ObservationBuilder` 将 patient_emotion 提供给患者，将 relative_emotion 提供给家属。患者生成器被要求结合当前情绪和可见信息回应；家属生成器明确只能用情绪调整措辞和语气，不能据此创造事实。

因此，前一轮产生的 fear 可以继续影响后续回应，而不是每轮只凭最新一句话重新猜测情绪。这提供了可检查的状态记忆，但并不保证生成模型一定严格遵循状态；“状态与台词是否一致”仍需评估。

情绪引擎与角色生成器在职责上分离，可以分别测试和替换。职责分离并不代表二者一定使用不同底层模型：当前运行脚本可以让多个模块使用同一个模型。因此，不能把模拟角色的回应自动当作独立验证情绪预测的证据。

### 6.2 影响终止条件，但不是直接控制治疗

当前 `termination.py` 仅在患者任一情绪达到 extreme 时触发情绪终止，家属 extreme 不会触发同样的 encounter 终止。这与共享提示词对 extreme 的概括并不完全一致，解释实验结果时必须保留这个区别。

当前没有“fear 达到某值就拒绝某项治疗”的明确执行规则。情绪也不会直接改写心率、血压、氧饱和度或治疗效果；生理适配器没有把 psych_state 作为专门的引擎输入。可能的后续影响主要经过角色对话、临床代理随后作出的决策，以及患者 extreme 引起的提前终止。

### 6.3 为复盘提供可定位的讨论材料

轮级情绪、消息、notes 和事件可以帮助教师定位“哪段沟通之后出现了什么模拟变化”，再回看原话与场景。它们提供的是模型轨迹中的关联及模型解释。若要讨论某个措辞的因果作用，应在相同起点下进行受控重放，而不是仅凭一次轨迹断言因果关系。

相关实现：[observation_builder.py](../ed_world_model/orchestration/observation_builder.py)、[prompting.py](../ed_world_model/agents/prompting.py)、[termination.py](../ed_world_model/state/termination.py)、[hybrid_physiology_adapter.py](../ed_world_model/adapters/hybrid_physiology_adapter.py)。

## 7. 如何用于医学生训练

最合适的起点是带教师反馈的形成性训练：允许学生练习、重试和讨论，而不是立即将模型标签用于高风险考试评分。当前代码提供了模拟部件；以下教学流程仍需学生交互入口、课程设计和评价工具支持。

### 7.1 训练“准确告知风险，同时照顾听者的接受能力”

学生面对同一个病例，可以练习直接告知、分段解释、确认理解、回应担忧等不同表达。Emotion engine 提供潜在的情绪后果，患者 agent 提供下一步回应，教师再评价信息是否真实、完整且适合当前情境。

关键教学原则是：准确告知严重病情之后，fear 或 sadness 仍然 present 可以是合理反应。好的沟通不应被定义为“所有情绪都降到 absent”。否则系统可能奖励隐瞒风险、空泛安慰或不真实的保证。

2025 年一项纳入 221 名三年级医学生的随机研究发现，示范性学习材料改善了模拟坏消息沟通中的言语和非言语表现。这支持在训练中采用示例与模拟演练，但该研究没有验证本项目、LLM 情绪标签或当前四维状态模型的教育效果。[Bosshard 等，Medical Education](https://pubmed.ncbi.nlm.nih.gov/40074561/)

### 7.2 训练信息组织与确认理解

Overwhelm 可以作为讨论信息负担的线索。教师可以要求学生把一段过密的说明重新组织为几个步骤，并邀请患者用自己的话复述重点。AHRQ 的 teach-back 方法正是通过患者或家属自己的复述来检查解释是否被理解。[AHRQ：Teach-Back](https://www.ahrq.gov/teamstepps-program/curriculum/communication/tools/teachback.html)

但情绪标签不能替代理解检查。未来教学评价必须独立判断患者是否正确复述了风险、下一步或注意事项；“overwhelm 降低”不能独立证明信息传达成功。

### 7.3 训练敏感信息询问与尊严保护

在用药困难、物质使用、隐私或其他敏感话题中，学生可以练习如何询问事实、探索障碍并避免人格指责。Shame 提供一个可讨论的反应维度。

教学目标不是回避困难问题，而是在获取必要信息时保持尊重。评价时还需要检查问诊是否完整、是否有诱导或歧视性假设；低 shame 不等于问诊质量高。

### 7.4 训练患者与家属的不同沟通需求

两套独立状态允许模拟“患者相对平静，家属仍担心”或“患者无法参与，主要向家属解释”等情况。学生需要识别谁是当前听者，分别回应，而不是假设所有人拥有相同信息和情绪。

AHRQ 的 check-back 强调确认信息是否被接收和理解，也适用于患者与家属。其教学目标可以用于设计沟通任务，但当前 engine 不直接给出闭环沟通是否完成的分数。[AHRQ：Check-Back](https://www.ahrq.gov/teamstepps-program/curriculum/communication/tools/checkback.html)

### 7.5 支持具体、可重试的复盘

一个建议的教学循环是：

```text
完成模拟 → 回看关键话语与反应 → 学生解释当时的判断
→ 教师核对临床与沟通标准 → 修改表达 → 在相同起点重试
```

复盘应同时查看原话、信息准确性、情绪预测、角色实际回应以及临床任务完成情况。AHRQ 将 debriefing 描述为通过回顾事件、分析行动与思考、提炼后续改进来支持学习的过程。[AHRQ PSNet：Debriefing for Clinical Learning](https://psnet.ahrq.gov/primer/debriefing-clinical-learning)

教师应能质疑模型标签。例如，“模型认为 sadness 应消失，但损失仍然存在”本身就是值得讨论的模型错误，而不应强迫学生接受。

## 8. 一个具体的教学场景

以下是课程设计示意，不是实际运行结果，也不规定唯一正确的情绪标签。

场景：清醒患者刚获知需要进一步紧急评估，目前 fear=present；尚未有证据表明危险已经解除。教师让学生解释接下来会发生什么。

| 学生表达 | 教学上要检查的内容 | 对情绪输出的合理解读 |
| --- | --- | --- |
| “别担心，肯定没事。” | 是否作出了信息不支持的保证？ | 即使模型预测 fear 下降，也不能据此判为好沟通 |
| “有几项问题需要尽快评估。我先解释眼前这一步，再说后面的安排。” | 是否准确传达紧迫性并组织信息？ | fear 仍存在并不表示失败；需结合后续理解与回应 |
| “我理解你害怕。你现在最担心的是哪件事？” | 是否回应情绪并找出具体担忧？ | 情绪保持 present 也可能是合理结果；识别担忧本身有教学价值 |
| “你能用自己的话说一下，我们接下来准备做什么吗？” | 是否真正确认理解，而不是只问‘懂了吗’？ | 需要独立检查复述内容，不能只看 overwhelm |

Emotion engine 的作用是让这些表达进入同一个可记录的模拟反馈过程。教师的作用是判断反馈是否合理，并把学生注意力引向准确沟通、理解与尊严，而不是追求最低情绪数值。

## 9. 对急诊相关工作的潜在帮助与当前成熟度

| 用途 | 可以怎样使用 | 当前还缺什么 |
| --- | --- | --- |
| 医学生与新入职人员的沟通演练 | 重复练习解释检查、处理担忧、坏消息和敏感问诊 | 学生输入入口、教师任务单、反馈界面与试点验证 |
| 医生—护士—患者—家属的团队演练 | 观察不同角色的表达如何影响模拟患者和家属 | 团队行为量表；当前没有医护人员自身压力、疲劳或情绪模型 |
| 教学病例与话术讨论材料制作 | 生成不同沟通版本，供教师筛选和标注 | 人工审核、信息真实性检查和示例质量控制 |
| 临床沟通 AI 的离线评价 | 在相同输入上比较模型与提示策略的情绪预测 | 独立人工标签、错误率与分层指标、避免同模型自评偏差 |
| 沟通流程或材料的早期设计 | 对不同解释顺序、措辞和信息密度进行模拟探索 | 用户研究及真实场景验证；不能直接推出实际流程改善效果 |

当前最有依据的产品定位是：急诊沟通模拟和研究的一个基础模块。它尚不是已经验证的临床心理评估工具，也不是完整的急诊服务流程或吞吐量优化模型。

将它用于真实工作辅助时，应先从培训、材料预审和模拟复盘开始。患者满意度、投诉、治疗依从性或安全结局的改善，都需要另外收集证据，不能由模拟中的四维情绪直接推出。

## 10. 当前限制会怎样影响教学解释

本节基于代码审查及本会话已经完成的本地模拟检查。本文只记录问题，没有修复运行代码。

| 当前限制 | 对教学或研究的影响 |
| --- | --- |
| `present → absent` 的“完全解决”与“有计划／有所缓解”表述未统一 | 相同表达可能获得不同降级判断，影响标签一致性 |
| 当前状态没有独立记录各情绪的触发原因 | 即使某项危险解除，也未必能确认所有恐惧来源已消失 |
| Extreme 边界依赖对听者崩溃可能性的推断 | 不能把一次预测当作实际失去参与能力的证明 |
| Turn loop 传给 adapter 的历史可能包含当前及同轮后续话语 | 评分可能提前受到后续消息影响，损害逐句因果解释 |
| 模型漏掉某个情绪字段时，解析可能用 absent 补齐 | 可能制造没有话语依据的情绪下降，不能归功于学生沟通 |
| 患者 extreme 会终止，家属 extreme 不会；adapter 还可能处理同批后续消息 | 不能把共享 prompt 的终止说明当成所有角色的真实行为 |
| 临床观察含 `last_turn_events`，情绪事件载荷可能带出内部等级 | 面向学生的界面需要显式过滤，不能声称内部标签已经严格隐藏 |
| 主要输入是文字，没有声音、表情和停顿的直接测量 | 不适合声称完整覆盖非言语沟通能力 |
| 当前默认从全 absent 起步，且情绪只由符合条件的话语触发 | 没有完整模拟入院前情绪、自身反思、自然消退、疼痛和环境刺激 |
| 现有评估是单条话语预测，且没有历史对话输入 | 单步指标不能直接代表完整 encounter 的长期行为质量 |

结构上，engine 提供了一条可解释的模拟更新路径；在证据上，仍需验证它对不同年龄、语言、关系和个体特点的判断是否合理。尤其不能仅凭某个 trait 就把人物固定为“容易失控”或“难合作”。

## 11. 如何验证它是否真正有用

应分别验证三个层面，因为它们回答不同问题。

### 11.1 引擎层：情绪转换是否符合人工标准

使用与 prompt 开发分开的人工标注集，明确标注者看到的上下文与模型输入。比较每种情绪和每种等级的表现，包括 macro-F1、extreme 的 precision/recall、变化检测、序数误差、无效输出率与耗时。多人标注的分歧应保留并审议，不能把歧义样本伪装成无争议真值。

当前评估脚本已经提供总体准确率、MAE、加权 kappa、变化检测和按情绪统计；部分建议指标仍需补充。脚本会跳过失败预测，并按话语文本匹配参考标签，正式比较前应处理失败统计和唯一条目标识问题。

Zero-shot、few-shot 和当前名为 react 的版本应在同一模型配置和同一批输入下比较。当前 react 实际增加的是单次内部结构化检查指导，并不执行工具交互。比较的是这些具体提示实现，而不是证明某一类提示方法在所有任务上更优。

### 11.2 世界模型层：状态是否产生合适的后续行为

在相同角色资料和对话条件下改变情绪状态，检查患者／家属回应是否按预期变化，同时不篡改临床事实。还应检查跨轮次连续性、角色可见信息边界、终止语义和日志完整性。

可以设置启用真实 engine 与使用 NoopEmotionEngine 的对照，但不能简单认为“没有 engine 就没有情绪化台词”：角色生成器仍可能根据话语和场景自行产生情绪表达。该对照检验的是显式情绪状态模块带来的额外价值。

### 11.3 教育层：学生是否学会了更好的沟通

建议先进行教师可接受性和小规模可用性试点，再设计学习效果研究。研究可比较相同病例、练习时长和教师支持条件下的训练方式，通过独立、尽可能盲法的评分者评估新的模拟或标准化病人任务，并观察学习保持与迁移。

学习指标应包括风险解释的准确性、对理解的确认、尊重与回应担忧、必要临床任务完成情况。学生满意度、平台练习次数以及 engine 判出的情绪下降只能作为补充信息，不能替代真实学习结果。

## 12. 建议的下一步

先完成状态转换语义和运行一致性修正，再由急诊教师审核一组小规模教学案例。之后接入学生发言入口和教师复盘视图，完整保存逐句话语、前后状态和模型解释，并允许教师纠正标签。最后进行独立的教育效果验证。

适合对外使用的定位表述是：

> 本项目的 emotion engine 将面向患者和家属的沟通话语转换为可持续跟踪的情绪状态，并将这些状态提供给急诊模拟中的后续角色交互。它为沟通演练、过程复盘和模型比较提供基础；其情绪预测有效性与教育效果需要分别验证。

这一定义保留了它最有价值的作用：让沟通在模拟世界中留下可检查、可讨论的后果，同时为临床事实、角色表现和教学评价保留各自独立的判断依据。
